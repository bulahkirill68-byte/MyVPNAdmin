# Reality Control

Русскоязычная панель управления **существующим Xray VLESS + REALITY + XTLS Vision** на одном VPS. Vue 3 + TypeScript, FastAPI, SQLAlchemy, Alembic, SQLite WAL. Xray остаётся в systemd на хосте, порт 443 и серверные ключи сохраняются.

## Быстрый запуск на Ubuntu 22.04 / 24.04 / 26.04

Нужны работающий Xray, Docker Engine с Compose plugin, Git и Python 3 на хосте. Установить Docker: <https://docs.docker.com/engine/install/ubuntu/>.

```bash
git clone https://github.com/bulahkirill68-byte/MyVPNAdmin.git
cd MyVPNAdmin
sudo bash scripts/install.sh
docker compose exec web python -m app.cli admin
```

Скрипт создаёт защищённую папку `data` (UID/GID 10001), `.env`, собирает приложение, выполняет миграции и запускает web/worker. Все контейнеры приложения работают **не от root**. После подготовки папок обычная команда запуска — `docker compose up -d --build`.

### Подключение существующего Xray

В защищённом файле `/root/xray-reality-access-*.txt` найдите **Public Key** (в новых версиях Xray он называется Password), а также публичный IPv4. Не используйте privateKey.

```bash
# Выполняется на VPS под root. Экспорт читает config.json, ничего в нём не меняет.
python3 scripts/export_xray.py --ip ВАШ_ПУБЛИЧНЫЙ_IP --public-key ПУБЛИЧНЫЙ_КЛЮЧ \
  | docker compose exec -T web python -m app.cli import
```

Импортируются все пользователи inbound `vless-reality` с исходными UUID и email. По умолчанию срок бессрочный; если уже был установлен срок, добавьте `--expires-at UNIX_TIMESTAMP_UTC` либо сразу задайте индивидуальные условия в панели. Сам Xray не хранит срок действия в конфиге, поэтому автоматически извлечь его невозможно. Повторный импорт отклоняется. Приватный ключ вообще не попадает в JSON экспорта или контейнер.

Ожидаемый API: `127.0.0.1:10085`, HandlerService + StatsService; включены пользовательские uplink/downlink уровня 0. Для безопасной проверки существующих UUID нужен RPC **GetInboundUsers**. Если установленная версия его не поддерживает, панель покажет ошибку применения; обновление Xray выполняется администратором отдельно. Установщик пользователя соответствует требованиям экспорта; **повторно запускать установщик Xray не нужно**.

### Открыть панель

На своём компьютере:

```bash
ssh -N -L 8000:127.0.0.1:8000 root@ВАШ_IP
```

Откройте **http://localhost:8000**. Панель слушает только IPv4 loopback. Не открывайте 8000 и 10085 в firewall. Домен и второй VPS не нужны.

## Что реализовано

- Администратор через локальный CLI, Argon2id, серверные сессии, CSRF, лимит попыток входа, аудит, logout.
- CRUD доступа: уникальные UUID/email, редактирование срока/квоты/комментария, пауза, возобновление, аннулирование, удаление с подтверждением; массовые действия.
- Бессрочный доступ / точное UTC-время / 1/7/30/90 дней; продление от текущей даты или действующего срока, предварительный расчёт.
- Трафиковые квоты с накоплением uplink + downlink, сбросы/рестарты счётчиков, события 80/95/100%, блокировка worker.
- Реальный typed gRPC HandlerService/StatsService; reconciliation активных пользователей и tombstone-записей после перезапуска; видимые pending/error/applied.
- Сохранение UUID первого клиента при импорте, ротация пользовательского UUID и токена без смены общего REALITY-ключа.
- VLESS, QR, копирование, офлайн-выдача через SSH CLI; хешированные токены **локальных** подписок.
- Наблюдаемый трафик, графики, CPU/RAM/диск, локальная проверка TCP 443, uptime Xray, журнал изменений.
- Тёмная/светлая тема, мобильная вёрстка, клавиатурные диалоги, reduced motion, русские подписи.
- Пресеты маршрутизации, приоритетные domain/IP правила, три слоя политики, drag-and-drop и стрелки, JSON-экспорт/импорт, предварительная проверка маршрута.
- SQLite WAL, Alembic, автоматические суточные копии, CLI восстановления, Docker multi-stage, healthchecks и CI.

## Важные границы MVP

1. **Xray на вашем VPS здесь не тестировался.** Перед выдачей массового доступа выполните [серверную приёмку](docs/DEPLOYMENT_RU.md#приёмка-на-действующем-vps). Тесты проверяют доменную логику и gRPC wire-контракт, но не заменяют подключение настоящего клиента.
2. Блокировка запрещает **новые** подключения после применения. API не гарантирует мгновенного завершения уже открытых соединений. Перезапуск Xray ради изменения пользователя не выполняется.
3. Квоты приблизительные: превышение возможно на трафик за интервал опроса (15 секунд по умолчанию), плюс время применения/сбоя API. Per-user bandwidth shaping и гарантии точной скорости не реализованы.
4. Xray runtime-пользователи восстанавливаются worker. При рестарте Xray статический пользователь из config.json может временно получить доступ до следующего успешного применения блокировки/ротации. Это **не fail-closed хостовый шлюз**; без изменения хостовой конфигурации нельзя устранить это окно. Runtime-пользователи без записи в config до reconciliation недоступны.
5. Статистика — наблюдаемые значения StatsService; трафик между последним опросом и аварийным рестартом может теряться. При первом импорте доступные текущие счётчики учитываются первым измерением; историческая помесячная статистика до панели не восстанавливается. Последняя активность — последний замеченный ненулевой прирост, не «онлайн».
6. Публичного HTTP/HTTPS сервиса подписок нет. URL `http://localhost:8000/sub/...` предназначен для SSH-туннеля и **не работает на телефоне через интернет сам по себе**. Используйте QR/ссылку и приватную передачу. Автообновление требует отдельно развёрнутого доступного HTTPS с действительным сертификатом.
7. VLESS-подписка содержит узлы; клиентские routing rules экспортируются отдельно. Android Per-app proxy настраивается в клиенте вручную. См. [ограничения маршрутизации](docs/ROUTING_LIMITATIONS.md).
8. Глобальные параметры Xray доступны только для чтения. Точного исторического SLA, управления systemd из web, 2FA/TOTP, внешних уведомлений и шейпинга скорости нет. Владелец — единственная роль MVP. Одна запись доступа = одно устройство; ограничение числа параллельных устройств не реализовано.

## Обслуживание

```bash
bash scripts/diagnose.sh
bash scripts/backup.sh
bash scripts/update.sh
# Имя смотрите в data/backups. Требуется явное подтверждение RESTORE.
bash scripts/restore.sh panel-ИМЯ.sqlite3
```

Не удаляйте `data`. Резервная копия содержит пользовательские UUID, хеши паролей и сессии — защищайте её. Храните отдельную копию вне VPS через SSH. После restore сессии удаляются.

## Разработка и проверки

```bash
python -m venv .venv
# Linux: source .venv/bin/activate ; Windows: .venv\Scripts\activate
pip install -e './backend[test]'
cd backend
pytest -q
ruff check app tests ../scripts
# После возврата в корень:
cd ../frontend
npm ci
npm run build
npm audit
# Браузерная проверка (использует отдельную временную БД и тестовый аккаунт):
npx playwright install chromium
npx playwright test
```

Для локального backend задайте `DATA_DIR` на отдельную тестовую директорию, выполните `alembic upgrade head` из backend, затем `python -m app.cli admin` и `uvicorn app.main:app --host 127.0.0.1 --port 8000 --no-access-log`. Фронтенд: `npm run dev` (Vite localhost с proxy). Для Compose dev: `docker compose -f compose.yaml -f compose.dev.yaml up -d --build`. Host network production рассчитан на Linux, не на Docker Desktop Windows.

Документы: [архитектура](docs/ARCHITECTURE.md), [безопасность](docs/SECURITY.md), [API](docs/API.md), [эксплуатация](docs/DEPLOYMENT_RU.md), [маршрутизация](docs/ROUTING_LIMITATIONS.md).

Playwright проверяет настоящий локальный HTTP API: вход, мастер пользователя, QR, паузу, продление, сохранение/тест маршрутов, резервную копию, светлую тему и мобильную навигацию без горизонтального переполнения. Скриншоты записываются в `artifacts/` (в CI — отдельный artifact). Фиктивных измерений Xray в тестовый UI не добавляется, при отсутствии Xray отображается «Нет данных». На Windows путь к Python из venv можно передать переменной `E2E_PYTHON`.
